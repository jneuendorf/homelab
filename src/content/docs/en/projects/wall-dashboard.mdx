# Wall Dashboard

A **fixed, wall-mounted tablet** showing a family screen: a left **app menubar** (Today, Calendar,
Routine, Lists), a top-right **user switcher**, and apps that can **read and write** data. It is a
small own shell in `projects/wall-dashboard/` — Node ≥ 22.18, no framework, no build for the server —
because it runs 24/7 and idle power matters.

> **Prerequisites:** a working Proxmox host
> ([Installing & Hardening Proxmox](/en/01-proxmox-install-harden)), and an understanding of the
> [LXC-vs-VM decision](/en/01-proxmox-install-harden#two-guest-types--pick-well).

> **Transition:** the old MagicMirror setup (`config/`, `modules/`, `install.sh`) still runs on
> **:8080** in the same CT until the shell reaches parity; the shell runs beside it on **:8090**.

## Why an own shell (not Home Assistant)

Home Assistant covers most widgets, but three goals tipped it:

| Need                    | Home Assistant                                                | Own shell                                            |
| ----------------------- | ------------------------------------------------------------- | ---------------------------------------------------- |
| **User switcher**       | HA users are logins; faking it costs users × cards conditions | Native: `forUser()` + sparse per-user overrides      |
| **Config**              | YAML / UI-stored, untyped                                     | Typed TS; each app owns its config                   |
| **Footprint (24/7)**    | HA OS VM, ~2 GB RAM, constant background activity             | Node in the existing LXC, ~100 MB RSS, ~0 % CPU idle |
| **Calendar write**      | Yes (CalDAV / Google)                                         | Not done — read-only ICS                             |
| **Phone notifications** | Companion app for free                                        | None                                                 |

Revisit HA (or put it _behind_ this shell as a data backend) if calendar writes or phone
notifications become must-haves. The full comparison lives in `projects/wall-dashboard/NOTES.md`.

**Low-power choices:** no server timers (weather / calendar are fetched on request and cached for
30 / 10 min); writes are pushed over SSE, never polled; the clock updates one text node per
second, everything else per minute; no CSS animations at rest; dark themes.

## Platform decision

| Question                     | Answer               | Why                                                                        |
| ---------------------------- | -------------------- | -------------------------------------------------------------------------- |
| Needs Docker?                | **No**               | Plain Node app with one runtime dependency (`ical.js`).                    |
| Wants host bind-mount?       | **No**               | Calendars come over the network (ICS); state is one SQLite file in the CT. |
| Hard isolation / own kernel? | **No**               | Internal, low-risk display app.                                            |
| **Result**                   | **unprivileged LXC** | Reuses CT 101 (created by the MagicMirror community-script).               |

## How it works

**`sdk/`** has two entry points. **`#sdk`** is the contract between shell and apps, imported by
both the server and the browser bundle: the types, `defineApp` / `defineDashboard`, the per-user
merge `forUser` and `secret` — nothing else, so an app in any framework needs only this.
**`#sdk/utils`** holds optional helpers for vanilla apps: the escaping `html` tag (+ `raw`), `$` (a
lookup that throws instead of returning `null`), `adoptStyle`, `pad` and the aligned timers
`every` / `everyMinute`.

**`server/`** is one Node process with no timers:

- **`main.ts`** serves the built files from `dist/public`, the SSE stream `/api/events`, a
  per-app key/value store `/api/<app>/kv/<key>` (SQLite; every write is broadcast over SSE), and
  forwards `/api/<app>/*` to that app's `server.ts` as a web-standard `Request`. An app with a
  `server.ts` owns its storage: the raw `kv/` route is closed for it, so its validation can't be
  bypassed.
- **`config.ts`** loads `dashboard.local.ts` if present, else the sanitized `dashboard.config.ts`.
- **`net.ts`** holds the request guards (see [Security](#security)).

The browser loads `index.html` + the shell bundle, opens **one** `EventSource`, and lazy-loads the
selected app's chunk. Apps read with `ctx.store.get` / `ctx.api(...)` and write with
`ctx.store.set` (a `PUT`); the server pushes the new value to every other screen.

### Security

There is no login: the screen is a shared kiosk. Instead every request passes three checks:

| Check                                                       | Blocks                                                                                                                                |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `isLan(ip)` — loopback, RFC1918, link-local                 | anything from outside the LAN (e.g. a stray port-forward)                                                                             |
| `isAllowedHost(Host)` — IP literal, localhost, `WALL_HOSTS` | **DNS rebinding**: a web page opened on any LAN device points its own domain at the CT and would otherwise use the API as same-origin |
| `isSameOrigin(Origin)` on non-GET                           | **CSRF**: a foreign page posting a form to an app handler                                                                             |

Responses carry a CSP (`default-src 'self'`, no framing), `nosniff` and `no-referrer`; 500s send no
error details. All markup goes through `html` (escaping), so feed titles and list entries can't
inject HTML. Calendar URLs stay in `.env` and are only read server-side.

- Reaching the screen by **name** (reverse proxy, `wall.home`) → list it in `.env`:
  `WALL_HOSTS=wall.home`. If that proxy is internet-facing, `isLan` sees the proxy's LAN IP —
  restrict access at the proxy.
- `dashboard.local.ts` is **bundled into the browser** too: never put a token in it as a literal,
  always `secret('NAME')`.
- Any LAN device can read and write all app data by design; plain HTTP until the reverse proxy
  adds TLS.

## The app contract

An app is one folder. Its `index.ts` calls `defineApp`, which turns a definition (id, menubar
label, defaults, lazy `ui` / `server` imports) into a **typed factory**: `routine({ deadline:
'07:40' })`. The server never loads UI code, and the browser only loads the active app's chunk.

<CodeSnippet file="projects/wall-dashboard/sdk/index.ts" start={48} end={69} />

- **UI:** `mount(el, ctx)` draws into `el` and returns a cleanup. Vanilla, React (`createRoot(el)`)
  or Svelte all fit; TS needs no per-app build (esbuild bundles it).
- **Server:** a `Handler` is `(req: Request, ctx) => Response` — web-standard, no framework,
  mounted at `/api/<app>/*`.
- **Store:** every app gets `ctx.store.get/set` (SQLite via `node:sqlite`). Each `set` is pushed to
  all screens; `ctx.subscribe(key, cb)` listens and is removed on unmount.

<CodeSnippet file="projects/wall-dashboard/sdk/index.ts" start={14} end={32} />

- **Per-user config:** layers are app defaults → instance config → `perUser[id]` (sparse,
  shallow). `ctx.config` is already resolved for the selected user; `ctx.configFor(id)` serves apps
  that show several users at once.
- **Secrets:** `secret('NAME')` reads `process.env` on the server and is `undefined` in the
  browser bundle — only the variable name ships to the client. Server code (`server.ts`) is
  stubbed out of the bundle entirely.

## Routine callbacks

The morning checklist shows one row per user with non-empty `items`; parents without items get no
row. Tap to check off; state lives in the server store, so every screen agrees, and it resets per
day. First to finish gets the `leader` badge, finishing before `deadline` adds `beatDeadline`.

Per user, `items` and `badges` are a plain value **or** a `(ctx) => value` callback. Callbacks run
in the browser and are bundled, so — unlike MagicMirror's serialized callbacks — they may import
shared helpers.

## iCloud calendar — read-only ICS

Each feed needs a public ICS URL in its **`https://`** form (not webcal):

- **Your own iCloud calendar** → **Mac Calendar** → right-click it → **Share Calendar** → tick
  **Public Calendar** → copy the link. Unpublish → republish rotates a leaked token.
- **A subscribed calendar** → select it → **Edit** (or File → Get Info) shows the URL.
- **Shared with you via iCloud** (not subscribed) → no public ICS; ask the owner to publish it.

A feed with `user` belongs to that user (their color, their routine `ctx`); without `user` it is
family-wide and shown to everyone.

## Deploy from this repo

```bash
# (Mac) — sync the repo to the host
scripts/deploy.sh root@192.168.1.10

# (host) — push the shell into CT 101, build it there, (re)start the service
/opt/homelab/projects/wall-dashboard/install-shell.sh 101
```

The script checks for Node ≥ 22.18 in the CT, pushes **code only** to `/opt/wall-dashboard` —
`dashboard.local.ts`, `.env` and the data are never in the tarball, so a deploy can't clobber them —
builds inside the CT, and installs a systemd unit running as an unprivileged `wall` user:

<CodeSnippet file="projects/wall-dashboard/install-shell.sh" start={39} end={58} />

First deploy only — put the real config and secrets in place, then re-run `install-shell.sh`:

```bash
# (host)
pct exec 101 -- cp /opt/wall-dashboard/dashboard.config.ts /opt/wall-dashboard/dashboard.local.ts
pct exec 101 -- sh -c 'printf "CAL_KIND1=https://…\n" > /opt/wall-dashboard/.env && chmod 600 /opt/wall-dashboard/.env'
```

The calendar's "today" is the CT's local day — check its timezone (`timedatectl`). Logs:
`pct exec 101 -- journalctl -u wall-dashboard -f`.

## Editing the live config

The CT's ZFS subvol is mounted on the host whether the container runs or not, so edit
`dashboard.local.ts` / `.env` straight over the host's SSH (other CTID/storage: derive the path with
`pct config <ctid>` + `zfs list`), then rebuild:

```bash
# (Mac)
zed ssh://pve/rpool/data/subvol-101-disk-0/opt/wall-dashboard
ssh pve /opt/homelab/projects/wall-dashboard/install-shell.sh 101
```

esbuild strips types without checking them: a syntax error fails the build, a type error does not.
Typecheck config changes on the Mac first (`npm --prefix projects/wall-dashboard run check`).

## Tablet kiosk

- **iPad:** open the URL in Safari → **Guided Access** to lock it fullscreen; Settings → Display →
  **Auto-Lock: Never**; keep on charger.
- **Android:** **Fully Kiosk Browser** (or Fullscreen Immersive) pointed at the URL; disable
  screen timeout.
- Point at the reverse-proxy HTTPS name once that's up, else `http://<lxc-ip>:8090`. The selected
  user is remembered per device.
